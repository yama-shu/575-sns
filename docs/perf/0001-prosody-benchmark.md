# 性能測定 0001: 判定エンジン（prosody）

| 項目 | 内容 |
| --- | --- |
| 対象 | prosody の判定 API（`POST /v1/analyze`） |
| 目的 | [NFR-01-01](../requirements/01-requirements.md#nfr-01-性能)（P95 < 150ms）の検証と、[ADR-0003](../adr/0003-morphological-analyzer.md#速度eの検証) が実測前に置いた見込みの確認 |
| 実施日 | 2026-08-09 |
| コミット | `678292d` |
| 関連 | [#9](https://github.com/yama-shu/575-sns/issues/9) / [詳細設計 04 §8](../design/detail/04-test-design.md#8-性能テスト) |

## 1. 結論

**NFR-01-01 を大きな余裕をもって満たす。** 想定負荷では目標の 1/20 以下だった。

| 指標 | 目標 | 実測 |
| --- | --- | --- |
| 判定 API の P95（想定負荷 100 req/s） | < 150 ms | **6.98 ms** |
| 判定処理そのもの（HTTP を除く） | — | **0.04 ms** 前後 |
| 辞書のロード時間 | — | **128.6 ms**（起動時1回） |
| prosody のメモリ | ADR-0004 の見積り 400 MB | **315 MB**（ワーカー4） |

ただし2つの条件が付く。**どちらも設定の問題であり、判定ロジックの問題ではない。**

1. **ワーカー数を CPU 数に合わせる必要がある。** 既定の1のままでは同時50接続を受けきれず、68% の接続がリセットされた
2. 想定負荷でも 0.23%（7 / 3001）の接続リセットが残る。原因を特定できていない（[§7](#7-未解決の事項)）

## 3. 測定方法

### 実行方法

すべてスクリプト化してある。**引数を変えれば同じ手順で再現できる。**

```bash
./scripts/bench/run.sh --workers 4
./scripts/bench/run.sh --workers 4 --connections 100 --duration 60s
```

| ファイル | 役割 |
| --- | --- |
| [scripts/bench/run.sh](../../scripts/bench/run.sh) | 起動 → 入力生成 → 負荷 → 内訳 → メモリ → 環境記録 |
| [scripts/bench/generate_inputs.py](../../scripts/bench/generate_inputs.py) | 入力データ 250 件の生成と分類 |
| [scripts/bench/load.js](../../scripts/bench/load.js) | k6 の負荷シナリオ |
| [scripts/bench/stages.py](../../scripts/bench/stages.py) | 段階ごとの内訳 |

### 負荷生成ツール: k6

| 要件 | k6 を選んだ理由 |
| --- | --- |
| 同じ文を繰り返さない | リクエストごとに別の本文を送れる |
| 負荷生成側が足を引っ張らない | **arm64 のイメージがある**。当初 vegeta を検討したが amd64 のみで、ARM 機ではエミュレーションになり測定が歪む |
| 同時接続数・レートを調整できる | executor で指定できる |
| 正しく負荷をかけられているか監視できる | 投入レートと実測レートの差が出力される |

### 3つのシナリオ

**目的が異なるため分けている。**

| シナリオ | 方式 | 目的 |
| --- | --- | --- |
| `cold` | 250 件をちょうど1周 | **1件も重複しない**条件での応答時間 |
| `rate` | 100 req/s 固定 | **想定負荷での応答時間**。NFR-01-01 はこれで判断する |
| `load` | 待ち時間なしで限界まで | 捌ける上限（飽和試験） |

> **`load` だけを見て応答時間を語ってはならない。**
> 待ち時間なしの `constant-vus` はサーバが飽和するまで投げ続けるため、
> 得られるのは「限界での待ち行列の長さ」であって想定負荷での応答時間ではない。
> 最初の測定ではこれを取り違え、実態より10倍以上悪い数値を見ていた（[§8](#8-測定設計の誤りと訂正)）。

想定負荷 100 req/s の根拠。

- 判定はデバウンス 300ms を前提とする（[基本設計 04](../design/basic/04-screens.md#判定を呼ぶタイミング)）
- レート制限は 60回/分/ユーザー（[基本設計 05](../design/basic/05-api.md#レート制限)）
- 同時接続の想定は 1,000（[NFR-01-03](../requirements/01-requirements.md#nfr-01-性能)）
- このうち一部が同時に推敲していると見て 100 req/s とした

## 4. 測定条件

### 入力データ

**250 件すべてが異なる本文。** 同じ文を繰り返すと辞書の内部キャッシュが効いて実態より速く見える。

| 種別 | 件数 | 意図 |
| --- | ---: | --- |
| 定型に区切れる文 | 100 | 最も一般的なケース |
| 許容に区切れる文 | 50 | ズレの判定を通る |
| 総モーラ数で弾かれる文 | 50 | 早期リターンの効果を確認する |
| C単位で失敗し A単位で成功する文 | 50 | **最悪ケース（2回解析する）** |

種別は推測せず、**生成した文を実際に判定器へ通して確定させている**。
乱数の種を固定しているため、同じ 250 件を再生成できる。

### 負荷の条件

| 項目 | 値 |
| --- | --- |
| 同時接続数 | 50 |
| 実行時間 | 各シナリオ 30 秒 |
| prosody のワーカー数 | 4（CPU 数に合わせる） |
| タイムアウト | 10 秒 |

## 5. 測定環境

### 構築方法

```bash
git clone git@github.com:yama-shu/575-sns.git && cd 575-sns
./scripts/bench/run.sh --workers 4
```

Docker 以外に必要なものはない。イメージのタグはすべて固定してある。

### スペック

| 項目 | 値 |
| --- | --- |
| アーキテクチャ | `aarch64`（Apple Silicon） |
| CPU | 4 |
| メモリ | 3.84 GiB |
| Docker Engine | 24.0.6 |
| Docker Compose | 2.21.0 |
| prosody のイメージ | `575-prosody:runtime`（本番と同じもの） |

> **負荷生成側（k6）も同じ4 CPU を共有している。** 負荷が高い領域では
> 生成側と prosody が CPU を奪い合うため、飽和試験の数値は
> 「この環境での上限」であり、prosody 単体の上限ではない。

## 6. 測定結果

### A. 判定 API の応答時間

| シナリオ | リクエスト数 | P50 | P95 | P99 | max | エラー率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **`rate`（想定負荷 100 req/s）** | 3,001 | 3.92 ms | **6.98 ms** | 20.05 ms | 111.88 ms | **0.23%** |
| `load`（飽和） | 約 78,000 | 16.33 ms | 42.03 ms | 71.73 ms | 240.98 ms | 約 20% |

**NFR-01-01（P95 < 150ms）を満たす。** 想定負荷での P95 は目標の約 1/21。

種別ごとの応答時間に有意な差はなかった。**最悪ケース（A単位へ落ちる文）が全体を押し上げてはいない。**

| 種別 | P95 |
| --- | ---: |
| 定型 | 42.09 ms |
| 許容 | 42.24 ms |
| 総モーラ数で弾かれる | 41.98 ms |
| 最悪ケース（A単位） | 41.85 ms |

（`load` シナリオでの値。想定負荷ではいずれも 7ms 前後）

### B. 処理段階ごとの内訳

プロセス内で 200 回ずつ測定した平均（ミリ秒）。

| 段階 | 定型 | 最悪ケース |
| --- | ---: | ---: |
| 正規化 | 0.001 | 0.001 |
| **形態素解析（C単位）** | **0.015** | 0.009 |
| 読み解決 + モーラ計算 | 0.015 | 0.009 |
| 区切り探索 | 0.005 | 0.001 |
| **形態素解析（A単位）** | — | **0.026** |
| 早期判定 | 0.001 | 0.000 |
| **合計** | **0.036** | **0.046** |

**ボトルネックは形態素解析である。** 判定エンジン全体で 0.04ms 前後にしかならず、
[詳細設計 01 §6](../design/detail/01-prosody-algorithm.md#計算量) が
「支配的なのは形態素解析であり、探索ではない」と述べていたとおりだった。
区切り探索は形態素解析の 1/3 以下で、**ここを最適化しても全体はほとんど変わらない。**

応答時間 6.98ms のうち判定は 0.04ms、つまり **99.4% は HTTP とプロセス間の往復**である。

### C. 辞書のロード時間

**128.6 ms**（プロセス起動時に1回）。

リクエストごとには発生しない。`/readyz` がロード完了まで false を返すため、
ロード中の Pod にトラフィックが流れることもない。

### D. メモリ使用量

| サービス | 使用量 |
| --- | ---: |
| **prosody**（ワーカー4） | **315.4 MiB** |
| web | 34.7 MiB |
| db | 39.5 MiB |
| api | 2.6 MiB |
| 合計 | 392.2 MiB |

ワーカー1のときは 64 MiB だった（[#2 の測定](https://github.com/yama-shu/575-sns/issues/2#issuecomment-5223662452)）。
ワーカーごとに辞書が複製されるため、**ワーカー数に比例して増える**。

これは [ADR-0002 が判定エンジンを分離した理由](../adr/0002-tech-stack.md#判定エンジンを分離しないと何が起きるかbceの詳細)
（辞書のメモリが複製される）が、プロセス単位でも同じ形で現れたものである。

## 7. 未解決の事項

### 想定負荷でも 0.23% の接続リセットが残る

`rate` シナリオで 3,001 件中 7 件が `connection reset by peer` になった。

| 分かっていること | 内容 |
| --- | --- |
| prosody は落ちていない | `RestartCount=0` / `OOMKilled=false` / ERROR ログ 0件 |
| リクエストが届いていない | prosody 側のログに該当がない |
| 発生の偏り | シナリオ開始直後（50接続の同時確立）に集中している |

仮説は「接続確立のバーストが listen backlog を超えた」だが、**確認できていない**。

本番では Ingress が接続を保持するため、この形のバーストは起きにくいと考えられる。
ただし推測であり、[M5 のクラスタ構築](../issues/README.md#m5-公開)後に再測定して確かめる。

## 8. 測定設計の誤りと訂正

**最初の2回の測定は、測定方法そのものが誤っていた。** 記録として残す。

### 1回目: ワーカー数が1のまま

68% の接続がリセットされた。判定は CPU バウンドである（[NFR-03-03](../requirements/01-requirements.md#nfr-03-拡張性)）のに、
`PROSODY_WORKERS` の既定値 1 で測っていた。

さらに、`compose.yaml` が `PROSODY_WORKERS` を環境変数として宣言していなかったため、
**スクリプトから渡しても コンテナに届いていなかった**。compose.yaml を修正した。

### 2回目: 飽和試験を応答時間の測定と取り違えた

ワーカーを4にすると P95 は 51ms に改善したが、まだ 24% が失敗していた。

原因は `constant-vus`（待ち時間なし）で測っていたことである。この方式は
**サーバが飽和するまで投げ続ける**ため、1,650 req/s という想定をはるかに超える負荷になり、
得られるのは「限界での待ち行列」であって想定負荷での応答時間ではない。

一定レートのシナリオを追加したところ、P95 は **6.98 ms** になった。

| 測定 | P95 | エラー率 | 何を測っていたか |
| --- | ---: | ---: | --- |
| 1回目（ワーカー1・飽和） | 275 ms | 68% | 受けきれない状態 |
| 2回目（ワーカー4・飽和） | 51 ms | 24% | 限界での待ち行列 |
| **3回目（ワーカー4・想定負荷）** | **6.98 ms** | 0.23% | **想定負荷での応答時間** |

**「速い / 遅い」を語る前に、何を測っているのかを確かめる必要がある。**

## 9. ADR への反映

### ADR-0003（形態素解析器の選定）

ADR-0003 は SudachiPy の速度を**実測せず**「短文なら十分に速いはず」という見込みで採用し、
「実装フェーズでベンチマークを取り、想定を外していた場合は本 ADR を見直す」としていた。

**見込みは正しかった。** 形態素解析は 0.015〜0.026 ms で、
150ms の予算に対して 4桁の余裕がある。fugashi + UniDic への差し替えは不要である。

### ADR-0004（ホスティング先とインフラ構成）

prosody のメモリ見積り 400 MB に対し、実測は**ワーカー1で 64 MiB、ワーカー4で 315 MiB**だった。

ワーカー数を CPU に合わせると見積りに近づく。[#2 の時点で「積算が過大」と記録した](https://github.com/yama-shu/575-sns/issues/2#issuecomment-5223662452)が、
**ワーカーを増やせば見積りは妥当な水準になる**、と補正しておく。

いずれの ADR も結論は変わらないため、新しい ADR は起こさない。
