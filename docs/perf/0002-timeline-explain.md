## 1. 結論

| 対象 | 結果 |
| --- | --- |
| 全体タイムライン | **問題なし。** 20 行を読んで 20 件を返す。0.85 ms |
| フォロー中タイムライン（通常） | **問題なし。** 22 行を読んで 20 件を返す。1.19 ms |
| フォロー中タイムライン（フォロー比率が低い） | **要注意。** 2,259 行 / 1.72 ms |
| フォロー中タイムライン（極端な例） | **要改善。** 74,549 行 / 29.22 ms |
| カーソル方式 vs `OFFSET` | **設計の判断は正しい。** 深いページで 125 倍の差 |
| `blocks` の双方向除外 | 現規模では追加のインデックス不要 |

[NFR-01-02](../requirements/01-requirements.md#nfr-01-性能)（タイムライン取得の P95 < 300ms）は、
最悪の測定値 29.22 ms でも満たしている。ただし**フォロー中タイムラインだけは
投稿総数に比例して悪化する経路がある**。詳細は §6。

改善案（`LATERAL` への書き換え）は [#41](https://github.com/yama-shu/575-sns/issues/41) で実施した。
**一方的な改善ではない**（§10）。フォロー数が少ない利用者は速くなり、多い利用者は遅くなる。
上限が予測できることを理由に採用した。

実装は [api/internal/infra/postgres/timeline.go](../../api/internal/infra/postgres/timeline.go)。

## 3. 測定方法

### 実行方法

```bash
./scripts/bench/timeline_explain.sh            # 投入してから測定する
./scripts/bench/timeline_explain.sh --no-seed  # すでにあるデータで測定する
```

データの投入は [scripts/bench/seed_timeline.sql](../../scripts/bench/seed_timeline.sql)。

### 計測の条件

- `EXPLAIN (ANALYZE, BUFFERS)` を使う
- **同じクエリを6回実行し、1回目を捨てて残り5回の中央値を採る。**
  1回目はキャッシュが冷えており、ディスク読み込みの時間が混ざる。
  1回だけの値は実行ごとに 2〜3 割ぶれる
- 投入後に **`VACUUM ANALYZE`** を実行する

### `ANALYZE` だけでは足りない

当初は `ANALYZE` だけを実行していた。統計は更新されるが**可視性マップが整わない**ため、
Index Only Scan が選べずヒープを読む計画になる。

同じクエリを、投入直後と autovacuum が走ったあとで比べた結果。

| | 実行時間 | バッファ | 計画 |
| --- | ---: | ---: | --- |
| 投入直後（`ANALYZE` のみ） | 15.284 ms | 3,151 | Index Scan + ヒープ読み |
| autovacuum 後 | 16.552 ms | **519** | Index **Only** Scan（`Heap Fetches: 0`） |

実行時間はほぼ変わらないが、**バッファ数が 6 倍違う**。
本番では autovacuum が走るため、後者が定常状態である。
投入直後の値を記録すると、本番と食い違う数値を残すことになる。

投入スクリプトに `VACUUM ANALYZE` を入れた。以降の数値はすべてその後の測定である。

### 測定値のばらつき

中央値を採ってもなお、実行のたびに数値は動く。
同じ条件で3回測り直した全体タイムラインの中央値。

| 回 | 中央値 |
| ---: | ---: |
| 1 | 0.963 ms |
| 2 | 0.852 ms |
| 3 | 0.852 ms |

**小数第2位までを意味のある値として扱わない。**
本記録の数値は「この規模でこの桁」を示すものであり、
0.1 ms の差を比較する用途には使えない。

### 数値の出どころ

| 種類 | 取得方法 |
| --- | --- |
| 実行時間・読んだ行数・バッファ数 | `EXPLAIN (ANALYZE, BUFFERS)` の出力をそのまま転記 |
| 中央値 | 5回の測定値を並べ替えて中央を採る |
| 件数・割合 | `SELECT count(*)` の結果、およびその除算 |
| 測定環境 | `docker info` / `pg_settings` |

**外挿は §6-F の1件だけで、その旨を明記している。** 他はすべて実測値か、
実測値どうしの計算である。

## 4. 測定条件

### 投入したデータ

| テーブル | 件数 | 備考 |
| --- | ---: | --- |
| users | 1,000 | |
| posts | 120,000 | うち published かつ public が 102,585 |
| follows | 50,100 | |
| blocks | 549 | |
| likes | 13,909 | 測定の主体（利用者1）が 3,000 件 |

基本設計 03 §3 が求める「posts 10万行以上」を満たす。

### 分布の偏り

全員が同じ数の投稿を持つデータでは、実際とは違う計画が選ばれうる。

| 層 | 人数 | 1人あたりの投稿数 |
| --- | ---: | ---: |
| 上位 1% | 10 | 2,000 |
| 中位 19% | 190 | 400 |
| 下位 80% | 800 | 30 |

- 公開範囲は `public` : `followers` = 9 : 1
- 5% を論理削除済みにする（部分インデックスが削除済みの蓄積に強いことを確かめるため）
- ブロックは 0 件にしない。0 件だとプランナが Seq Scan を選び、判断できない（[#38](https://github.com/yama-shu/575-sns/issues/38)）

### 測定の主体

| 利用者 | フォロー数 | フォロー先の投稿が全体に占める割合 |
| --- | ---: | ---: |
| 利用者1 | 150 | 61.99% |
| 利用者700 | 50 | 1.25% |
| 利用者999（作為的） | 1 | 0.03%（29 件） |

フォロー数 150 は、[ADR-0005](../adr/0005-timeline-strategy.md) が
「1ユーザーあたりの平均フォロー数」を監視指標としているため、
平均より多い側を想定して選んだ。

## 6. 測定結果

### A. 全体タイムライン

```
Limit  (actual time=0.735..0.845 rows=20.00 loops=1)
  ->  Nested Loop Anti Join
        Join Filter: (((b.blocker_id = 1) AND (b.blocked_id = p.author_id))
                   OR ((b.blocker_id = p.author_id) AND (b.blocked_id = 1)))
        ->  Index Scan Backward using posts_pkey on posts p
              (actual time=0.051..0.056 rows=20.00 loops=1)
              Filter: status = 'published' AND visibility = 'public'
              Rows Removed by Filter: 2
実行時間の中央値（5回）: 0.852 ms
```

| 確認項目 | 期待 | 実測 |
| --- | --- | --- |
| `posts` に Seq Scan が出ない | Index Scan | Index Scan Backward |
| 早期終了している | 読んだ行数が 20 前後 | **22 行**（20 + 除外 2） |

**部分インデックス #6 ではなく主キーが使われている。** 述語（published かつ public）が
全体の 85% に当てはまるため、プランナは主キーを逆順に辿って絞るほうが安いと判断した。
どちらでも「並べ替えずに上位 20 件を取れている」ことに変わりはない。

### B. フォロー中タイムライン

フォロー先の投稿が全体に占める割合によって、読む行数が変わる。

| 測定の主体 | 割合 | 読んだ行数 | 実行時間（5回の中央値） |
| --- | ---: | ---: | ---: |
| 利用者1 | 62.02% | 22 | 1.188 ms |
| 利用者700 | 1.25% | 2,259 | 1.717 ms |
| 利用者999（1人だけフォロー） | 0.03% | **74,549** | **29.218 ms** |

いずれも `posts_pkey` を逆順に辿り、1行ずつ `follows` を引いて絞る計画になる。

```
->  Index Scan Backward using posts_pkey on posts p  (rows=74549.00 loops=1)
      Filter: (status)::text = 'published'
->  Memoize  (loops=74549)
      ->  Index Only Scan using follows_pkey on follows f
            Index Cond: ((follower_id = 999) AND (followee_id = p.author_id))
```

**設計が想定したインデックス #7（`(author_id, id DESC)`）は使われていない。**

読む行数は「20 ÷ フォロー先の投稿の割合」に比例する。
割合が同じなら投稿総数が増えても行数は変わらないが、
**割合が下がるほど直線的に増える**。

### C. カーソルの深さによる違い

全体タイムラインを深い位置から取得した場合。

| cursor | 実行時間（5回の中央値） |
| ---: | ---: |
| なし（先頭） | 0.852 ms |
| 119,000 | 1.209 ms |
| 60,000 | 1.127 ms |
| 1,000（末尾付近） | 0.168 ms |

**深さによる劣化はない。** ADR-0005 がカーソル方式を選んだ狙いどおりである。

### D. `OFFSET` 方式との比較

[基本設計 03 §5](../design/basic/03-database.md#なぜ-offset-を使わないか) の
「`OFFSET` はページが深くなるほど線形に遅くなる」を数値で確かめた。

同じ条件（`status='published' AND visibility='public'`、20件取得）で比較する。

いずれも5回の中央値。

| 位置 | `OFFSET` 方式 | カーソル方式 | 差 |
| ---: | ---: | ---: | ---: |
| 先頭 | 0.060 ms | 0.231 ms | カーソルのほうが遅い |
| 1,000 件目 | 0.201 ms | 0.081 ms | 2.5 倍 |
| 20,000 件目 | 2.046 ms | 0.120 ms | 17 倍 |
| 100,000 件目 | **10.395 ms** | **0.083 ms** | **125 倍** |

先頭ページだけは `OFFSET` のほうが速い。`OFFSET 0` は読み飛ばしが無く、
カーソル方式は `p.id < 120001` という条件の評価が加わるためである。
**差は 0.17 ms であり、実用上の意味はない。**

読み込んだバッファ数の差がそのまま出ている。

| 位置 | `OFFSET` のバッファ | カーソルのバッファ |
| ---: | ---: | ---: |
| 先頭 | 4 | 7 |
| 1,000 件目 | 8 | 7 |
| 20,000 件目 | 106 | 7 |
| 100,000 件目 | **519** | **7** |

**カーソル方式はどの位置でも 7 で変わらない。**

`OFFSET 100000` は 10 万行を読み飛ばすために 10 万行を実際に読む。
カーソル方式はインデックス上の位置へ直接ジャンプする。

無限スクロール（[FR-03-03](../requirements/01-requirements.md#fr-03-閲覧)）で
利用者が深いページへ進むほど差が開く。設計の判断は正しかった。

### E. `blocks` の双方向除外

```
->  Materialize  (actual time=0.004..0.004 rows=50.00 loops=20)
      ->  Seq Scan on blocks b  (actual time=0.008..0.030 rows=50.00 loops=1)
            Filter: ((blocker_id = 1) OR (blocked_id = 1))
            Rows Removed by Filter: 499
            Buffers: shared hit=4
```

Seq Scan だが、**テーブル全体を1回だけ読んで結果を保持している**（`loops=1`）。
自分に関係する 50 行を取り出したあとは、Anti Join がその 50 行だけを見る。
549 行のテーブルを 4 ページ読むだけであり、これがボトルネックになることはない。

**追加のインデックスは不要。** [基本設計 03 §3](../design/basic/03-database.md) の
「必要な場所にだけ張る」に従い、予防的に足さない。

`blocks` が数万行規模になったときにプランナが主キーを使う計画へ切り替えるかは、
その時点で再測定する。主キーは `(blocker_id, blocked_id)` の順だが、
双方向の条件は**両方の枝で `blocker_id` を等値で絞る**ため、そのまま使える。

### F. `liked_by_me` の取得

```
SubPlan 2
  ->  Bitmap Heap Scan on likes l  (actual time=0.101..0.301 rows=3000.00 loops=1)
        Recheck Cond: (user_id = 1)
        Buffers: shared hit=36
```

`EXISTS` が**ハッシュ化された副問い合わせ**になり、
閲覧者のいいねを1回だけ読んでからハッシュで照合している。
投稿20件ぶんのループにはなっていない（`loops=1`）。N+1 は起きていない。

ただし**閲覧者のいいね数に比例する**。3,000 件で 0.28 ms・バッファ 36。

| いいね数 | 値 | 出どころ |
| ---: | --- | --- |
| 3,000 | 0.28 ms | **実測** |
| 100,000 | 9 ms 前後 | **外挿**（比例と仮定して 33 倍。測定していない） |

外挿の前提は「所要時間がいいね数に比例する」ことだが、
実際にはハッシュの構築コストやメモリ超過時のディスク書き出しが加わりうる。
**この行を根拠に判断してはならない。** いいね機能の実装後、実データで測り直す。

## 7. 測定設計の誤りと訂正

### 投稿 ID と著者 ID を相関させてしまった

1回目の測定では、フォロー中タイムライン（利用者1・フォロー比率 62%）が
**41,440 行を読んで 20 件を返した**。フォロー比率が高いのに読む行数が多く、辻褄が合わない。

原因は投入スクリプトにあった。著者ごとにまとめて投稿を挿入したため、
`BIGSERIAL` が著者順に並び、**投稿 ID と著者 ID が相関**していた。

```
利用者1〜10    → 投稿 ID の若い側に集中
利用者800〜1000 → 投稿 ID の新しい側に集中
```

タイムラインは ID 降順に読む。新しい投稿がフォローしていない利用者に偏っていれば、
フォロー先の投稿にたどり着くまで大量に読み飛ばすことになる。
これは**現実には存在しない分布**であり、測定していたのはデータの作り方の癖だった。

投入時に `ORDER BY random()` を加えて相関を消した。

```
corr(id, author_id) = -0.0037
```

再測定で 41,440 行 → 22 行になった。

**この誤りに気づけたのは、フォロー比率と読んだ行数が矛盾していたためである。**
実行計画の数値どうしが整合するかを確かめないと、こうした癖を実装の問題と誤診する。
[#9](https://github.com/yama-shu/575-sns/issues/9) で飽和試験を応答時間の測定と取り違えたのと同じ種類の誤りである。

### `ANALYZE` だけで測ってしまった

投入後に `ANALYZE` しか実行していなかったため、可視性マップが整わない状態で測定していた。
`OFFSET 100000` のバッファ数を **3,151** と記録したが、autovacuum が走ったあとは **519** である。

実行時間はほぼ同じ（15.3 → 16.6 ms）で結論は変わらないが、
記録した数値は本番の定常状態と食い違っていた。

投入スクリプトに `VACUUM ANALYZE` を追加し、すべて測り直した（§3）。

**PR のレビュー中に、記録した数値を再現しようとして気づいた。**
一度測って書き写すだけでは、測定条件の抜けに気づけない。

### 1回だけの測定値を載せていた

当初は各クエリを2回実行して2回目を採っていたが、実行ごとに 2〜3 割ぶれる。
6回実行して1回目を捨て、残り5回の中央値を採るよう変更した。

初版に載せていた「フォロー中タイムライン 47.50 ms」は、
中央値では 29.22 ms である。**桁は変わらないが、単発の値を代表値として
扱っていた**ことに変わりはない。

## 8. 改善案の検討（#41 で実施済み）

フォロー中タイムラインを `LATERAL` で書き換えると、
設計が想定したインデックス #7 を使う計画になる。

```sql
SELECT t.* FROM (
  SELECT p.* FROM follows f
  JOIN LATERAL (
    SELECT * FROM posts p
    WHERE p.author_id = f.followee_id AND p.status = 'published' AND p.id < :cursor
    ORDER BY p.id DESC LIMIT :limit
  ) p ON true
  WHERE f.follower_id = :me
) t ORDER BY t.id DESC LIMIT :limit;
```

```
->  Index Only Scan using posts_author_timeline_idx on posts p
      (actual time=0.009..0.010 rows=20.00 loops=50)
```

5回の中央値で比較する。

| 測定の主体 | フォロー数 | 現行 | `LATERAL` |
| --- | ---: | ---: | ---: |
| 利用者1 | 150 | **0.836 ms** | 3.309 ms |
| 利用者700 | 50 | 1.717 ms | **0.534 ms** |
| 利用者999 | 1 | 29.218 ms | **0.222 ms** |

`LATERAL` は読む行数が「フォロー数 × `limit`」で頭打ちになり、
**投稿総数に依存しない**。一方、フォロー数が多い利用者では現行のほうが速い
（利用者1 で 0.836 ms 対 3.309 ms）。

**どちらが常に速いというものではない。**
書き換える理由は速さではなく、悪化の上限を予測できることにある。

> **本節は検討時点の記録である。** 実装後の測定は §10 にある。
> 本節の `LATERAL` の数値は簡略版のクエリで測ったもので、実装と同じ形ではない。

### 検討時点で「いま書き換えない」とした理由

- 最悪でも 29.22 ms であり、[NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の 300ms に対して余裕がある
- [ADR-0005](../adr/0005-timeline-strategy.md) は方式変更の判断基準を
  「P95 が 300ms を超え続けること」としており、その段階にない
- 書き換えは挙動の同一性を検証する必要があり、測定の記録とは別の作業である

**[#41](https://github.com/yama-shu/575-sns/issues/41) として起票した。** 悪化の条件（フォロー比率の低下・投稿総数の増加）は
本記録に残したため、判断の材料は揃っている。

## 10. `LATERAL` への書き換え（#41）

§8 の改善案を実装し、同一データで測り直した。

### 結論

**採用する。** ただし**一方的な改善ではない**。悪化する場合がある。

| フォロー数 | 旧（素朴な JOIN） | 新（`LATERAL`） |
| ---: | ---: | ---: |
| 1 | **28.254 ms**（68,365 行） | 0.571 ms（20 行） |
| 50 | 1.254 ms（1,610 行） | 3.497 ms（20 行） |
| 150 | **0.357 ms**（35 行） | 5.960 ms |
| 550 | 0.562 ms（24 行） | **19.837 ms** |

いずれも投稿 120,000 行・5回の中央値。行数は `posts` を読んだ数。

新旧で**悪化する条件が入れ替わる**。

| | 悪化する条件 | 上限 |
| --- | --- | --- |
| 旧 | フォロー先の投稿が全体に占める割合が低い | **無い**。投稿総数に比例して増える |
| 新 | フォロー数が多い | フォロー数 × `limit` で頭打ち |

### なぜ新を採るのか

**上限が予測できるため。**

旧の費用は「`limit` ÷ フォロー先の投稿の割合」で決まる。フォロー数を変えなくても、
**サービスに投稿が積み上がるだけで悪化し続ける**。上限が無い。

新の費用はフォロー数に比例し、投稿総数に依存しない。
人が際限なくフォローすることはないため、上限が読める。

もう1つの理由は、**旧の悪化条件が「新規利用者」そのもの**であることである。
登録直後にフォローが1〜2人の状態は、サービスが若いほど多い。
28 ms は許容範囲だが、投稿が 10 倍になれば同じ利用者が同じ操作で 10 倍待つ。

### 代償

フォロー数 150 の利用者で **0.357 ms → 5.960 ms（17 倍）** になる。

[NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の 300ms に対しては
どちらも十分に速く、体感には現れない。**遅くなること自体は事実として記録しておく。**

フォロー数が 5,000 に達すると 180 ms 前後になる計算だが、これは**外挿であり測定していない**。
実際にそこまでフォローする利用者が現れたら測る。

### ブロックの除外は1回にまとめる

最初の実装では、フォロー先ごとに `NOT EXISTS` を評価していた。

```sql
-- ❌ フォロー先ごとに評価する
WHERE f.follower_id = $1
  AND NOT EXISTS (SELECT 1 FROM blocks b WHERE ...)

-- ✅ 相手の一覧を1回で集めてから除外する
WHERE f.follower_id = $1
  AND f.followee_id <> ALL (
    SELECT CASE WHEN b.blocker_id = $1 THEN b.blocked_id ELSE b.blocker_id END
    FROM blocks b WHERE b.blocker_id = $1 OR b.blocked_id = $1)
```

| フォロー数 550 | 実行時間 |
| --- | ---: |
| フォロー先ごとに評価 | 49.221 ms |
| 1回にまとめる | **19.837 ms** |

**フォロー数が多いほど効く。** 書き換えの効果を測る前にこれを直さないと、
`LATERAL` の費用を過大に見積もることになる。

### 振る舞いが変わらないことの確認

`LATERAL` は「フォロー先ごとに上位 `limit` 件を取ってから全体で上位 `limit` 件を選ぶ」。
ある投稿が全体の上位 `limit` 件に入るなら、その投稿者の中でも上位 `limit` 件に入るため、
取りこぼしは起きない。

これを結合テストで固定した。

- 素朴なクエリを**基準**として同じ結果を返すこと（`limit` 5 / 20 / 50、5ページ分）
- 1人が `limit` を超える連続投稿を持つ状況を含めること
- カーソルで全件を重複・欠落なくたどれること

内側の `LIMIT` を外側より小さくすると、基準との比較が落ちることも確認した。

```
$ # 内側を LIMIT 5 に変えて実行
--- FAIL: TestHomeTimelineMatchesReference
    1ページ目の件数が違う: 14, want 20
--- FAIL: TestHomeTimelineCursorCoversAllPosts
    取得できた件数が違う: 26, want 44
```

### §8 の見積もりとの差

§8 では `LATERAL` を「利用者700 で 0.534 ms」と書いたが、実装後は 3.497 ms だった。

**測っていたクエリが違った。** §8 の測定はブロックの除外と `users` の JOIN を
含んでいない簡略版で、実装と同じ形ではなかった。改善案の見込みを述べる段階で
簡略版を測ったのは誤りである。本節の数値は実装と同じクエリで測り直したものである。
