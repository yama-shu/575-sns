## 実装上の注意

### 判定は Server Action で中継する

当初は Route Handler（`web/src/app/api/...`）を使う予定だった。
「Server Action は呼び出しのたびに現在のページを再描画するため、
入力中に何度も走る判定には重い」と考えたためである。

**測ったところ、この前提は誤りだった。**
検証用のページと Server Action を用意し、ページの描画回数を数えた。

```
GET  /probe          → [probe] page rendered: 2
POST /probe (action) → 85 bytes / [probe] page rendered は増えない
POST /probe (action + Next-Router-State-Tree) → 同上
```

応答は戻り値だけで、ページの再描画は起きない
（`revalidatePath` などを呼ばない限り）。

Route Handler を使う理由が消えたため、**他の画面と揃えて Server Action にする**。
web に2つ目の HTTP 面を増やさずに済み、Origin 検査による CSRF 対策も
[#48](https://github.com/yama-shu/575-sns/issues/48) と同じ形で効く。

ブラウザが web としか通信しない点（[基本設計 01 §6](../design/basic/01-architecture.md)）は変わらない。

### 応答の追い越し

判定は非同期で、**後から投げた要求が先に返ることがある**。
そのまま表示すると、古い本文に対する判定が新しい本文の結果を上書きする。

要求に連番を振り、**最新の要求の応答だけを採用する**。

### 読みを見せる

[基本設計 04 §3](../design/basic/04-screens.md#なぜ区切りとモーラ数を必ず見せるのか) が
「システムが読みを誤っている場合も、読みを表示していればユーザーが気づける」
としている。

`CheckSegment.reading` を表示する。これが無いと、
「一日」を `イチニチ` と読まれたのか `ツイタチ` と読まれたのかが分からず、
モーラ数が合わない理由にたどり着けない。

### 破調のときに「あと何音」を出す

[基本設計 04 §3](../design/basic/04-screens.md#なぜ区切りとモーラ数を必ず見せるのか) の
「❌ 悪い例: 五七五になっていません」を避ける。

`CheckSegment.diff`（規定との差。字余りが正）から算出する。
`segments` が `null`（五七五に区切れない）の場合は `total_mora` と `reason` を使う。

### JavaScript が無い場合はページとして動かす

[NFR-06-03](../requirements/01-requirements.md#nfr-06-ユーザビリティ) は
「主要な操作はキーボードのみで完結できる」ことを求めている。詠むことは主要な操作である。

[#50](https://github.com/yama-shu/575-sns/issues/50) の「もっと読む」と同じ形にする。
「詠む」はモーダルを開くボタンであると同時に**リンク**でもあり、
JavaScript が無ければ投稿ページへ遷移する。

リアルタイム判定は JavaScript が要るため、その経路では**投稿時のサーバー側判定だけ**が働く。
[FR-02-05](../requirements/01-requirements.md#fr-02-投稿詠む)（保存前にサーバー側で再判定）があるため、
破調が保存されることはない。

### クライアントの判定を信用しない

[基本設計 01 §4](../design/basic/01-architecture.md) のとおり、`POST /posts` は判定結果を受け取らない。
web は判定結果を**送らない**。送っても読まれないうえ、送る実装があると
「クライアントの判定で決まる」という誤解を生む。

投稿ボタンを無効にするのは体験のためであり、**防御ではない**。

### 投稿後にどこへ行くか

[基本設計 04 §2](../design/basic/04-screens.md#2-画面遷移図) の遷移図は
`S-07 -.投稿完了.-> S-02`（フォロー中タイムライン）としている。

**しかしフォロー中タイムラインに自分の投稿は出ない。**
[基本設計 03](../design/basic/03-database.md) のホームタイムラインの問い合わせは
`follows` を起点にしており、自分をフォローしていない限り自分の投稿は含まれない。
詠んだ直後に「何も無い画面」へ送られることになる。

実機で確かめた。tarou が hanako をフォローした状態で両者が投稿すると、

```
tarou の home   → [('hanako', '古池や蛙飛び込む水の音')]
tarou の public → [('tarou', '柿くへば…'), ('hanako', '古池や…'), ('aoi', '古池や…')]
```

遷移先を全体タイムラインに改め、
[基本設計 04 §2](../design/basic/04-screens.md#2-画面遷移図) を修正する。
