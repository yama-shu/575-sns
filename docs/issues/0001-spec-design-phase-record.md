## 背景・目的

「投稿本文が五七五でなければ投稿できない SNS」というアイデアを、
実装に着手できる状態まで具体化する。

実装を始めてから「そもそも何を作るのか」「なぜこの構成なのか」を考え直すことになると、
手戻りが大きい。特に以下は先に決着させておく必要がある。

- 「多少の字余り・字足らずは許容する」の「多少」が数値で定義されていない
- 判定エンジンをどう実現するか（形態素解析器の選択肢が言語によって異なる）
- 無料枠の範囲でどこまで非機能要件を満たせるか

## やること

- [ ] 要件定義書を作成する
- [ ] 主要な意思決定を ADR として記録する
- [ ] 基本設計（システム構成・ドメインモデル・DB・画面・API）を作成する
- [ ] 詳細設計（判定アルゴリズム・クラス設計・エラー設計・テスト設計）を作成する
- [ ] 実装フェーズの Issue を起票する

## 完了条件

- [ ] 要件定義書に機能要件・非機能要件が ID 付きで列挙されている
- [ ] 要件定義書の「未決事項」がすべて決着し、決定内容へのリンクが張られている
- [ ] すべての ADR に「採用しなかった案とその理由」が記載されている
- [ ] 詳細設計を読めば、判定アルゴリズムを他人が実装できる粒度になっている
- [ ] 次のマイルストーンの Issue が起票されている

## やらないこと

- 実装
- 画面のビジュアルデザイン（レイアウトの構造までとし、配色・タイポグラフィは扱わない）
- 第2版以降の機能（返歌・お題・検索・通知）の詳細設計

## 検討の経緯

主要な判断は ADR に清書済み。以下に要点と、ADR に至った経緯を残す。

### 字余り・字足らずの許容範囲（[ADR-0001](../adr/0001-onsuritsu-tolerance.md)）

4案を比較した。当初は「合計17±2モーラ」という単純な案を検討したが、
これだと「今日は本当に疲れた一日だったな」（17モーラだが五七五ではない）が通ってしまい、
プロダクトのコンセプトが崩壊することに気づいた。区切りを見ない案はすべて却下。

採用案は「各句 4〜6 / 6〜8 / 4〜6 かつズレは最大1句」。

**検討中の発見**: 当初この案に「合計16〜18モーラ」という第3の条件を加えようとしたが、
ズレが最大1句である以上、他の2句は規定値ちょうどになるため、
合計は必然的に 17±1 に収まる。第3の条件は導出可能であり、
書くと条件が重複してバグの温床になる。**条件を2つに削った。**

結果として、投稿可能なパターンが「定型1通り + 許容6通りの計7通り」に確定し、
テスト設計での網羅が可能になった。

### 技術スタックとサービス分割（[ADR-0002](../adr/0002-tech-stack.md)）

TypeScript 一本のモノリスが最も開発しやすいが、判定エンジンを分離できない。
分離しない場合の決定的な問題は**メモリ**だった。

形態素解析の辞書は数十〜数百 MB をメモリに常駐させる。
判定を API サーバーに同居させると、タイムライン負荷で API を増やすたびに
辞書が複製される。判定（CPU バウンド・辞書が重い）とタイムライン（I/O バウンド・軽い）は
負荷特性がまったく違うため、スケール単位を分けたい。

3サービス構成（web / api / prosody）を採用。1人開発には重いが、
`docker compose` で吸収し、依存を一方向に固定することで管理する。

### 形態素解析器（[ADR-0003](../adr/0003-morphological-analyzer.md)）

当初 UniDic の「発音形」が必要だと考えていた（`今日は` → `キョーワ`）。
しかし検証したところ、**モーラ数を数える目的では読みと発音形の結果が常に一致する**。

```
キョウハ = キョ/ウ/ハ = 3モーラ
キョーワ = キョ/ー/ワ = 3モーラ
```

これにより UniDic を選ぶ理由が消え、C++ ビルド依存と数百 MB の辞書を回避できた。
分割粒度を A/B/C で切り替えられる SudachiPy を採用。

### ホスティング（[ADR-0004](../adr/0004-hosting-and-infrastructure.md)）

「有償サービスはできるだけ使わない」という制約と、
「稼働率 99.5% / 単一サーバー障害での全断回避」という非機能要件が正面から衝突した。

**この衝突は解消できなかった。**
アプリケーション層は無料枠の複数ノードで冗長化できるが、
PostgreSQL の冗長化は1人運用で維持できる複雑度を超える。

要件を下げるのではなく、**DB が単一障害点として残ることを記録して運用開始する**判断とした。
中途半端なフェイルオーバーはスプリットブレインを招き、単一構成より危険なため。
代わりにバックアップとリストア訓練で復旧可能性を担保する。

### タイムライン方式（[ADR-0005](../adr/0005-timeline-strategy.md)）

Push 型（fan-out on write）は読み込みが速いが、
ブロック・削除・運営による非表示化のたびに事前計算済みのタイムラインを
遡って修正する必要がある。修正漏れは「ブロックしたのに相手の投稿が見え続ける」
という健全性機能として致命的な不具合になる。

Pull 型を採用。想定規模では十分であり、Redis 等の追加リソースも不要。

### 認証方式（[ADR-0006](../adr/0006-authentication.md)）

JWT を検討したが、**即時失効できない**点が利用停止機能と両立しない。
利用停止にしてもトークンの有効期限まで投稿し放題になる。

失効リストで回避する案もあるが、それはステートフルであり JWT を選ぶ理由が消える。
Cookie + PostgreSQL セッションを採用。Redis を足さないのは、
その分のメモリを判定エンジンの辞書に回したいため。
