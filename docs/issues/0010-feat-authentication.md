## 背景・目的

[ADR-0006](../adr/0006-authentication.md) で決めた Cookie + PostgreSQL セッション方式を実装する。

api にはまだ業務ロジックが無く、ヘルスチェックとマイグレーションだけである。
認証は投稿・タイムライン・いいねのすべてが前提とするため、
**ここが入らないと M2 以降が積み上がらない**。

DB のスキーマは [#20](https://github.com/yama-shu/575-sns/issues/20) で用意済みで、
`users` / `sessions` テーブルと制約はすでにある。

## 実装上の注意

### パスワードのハッシュ化

[NFR-04-01](../requirements/01-requirements.md#nfr-04-セキュリティ) は「ソルト付きハッシュ」としか定めていないため、ここで選ぶ。

| 方式 | 利点 | 欠点 |
| --- | --- | --- |
| **bcrypt** | 標準的で実績が長い。ソルトを内包し、コストを1つ調整するだけ。`golang.org/x/crypto` にある | メモリ困難性がない。入力が 72 バイトで切り捨てられる |
| **argon2id** | メモリ困難性があり、GPU 攻撃に強い。現在の推奨 | 3つのパラメータを環境に合わせて調整する必要がある。誤った設定は bcrypt より弱くなりうる |
| **scrypt** | メモリ困難性がある | パラメータ調整が要る。採用例は argon2id に流れている |
| **PBKDF2** | FIPS 準拠 | メモリ困難性がない。要件が無いのに選ぶ理由がない |

**bcrypt を採用する。** 理由は3つ。

1. パラメータがコスト1つで、**誤設定の余地が小さい**。1人開発では調整の失敗が最大のリスクである
2. 72 バイトの切り捨ては、パスワードの最大長を 72 バイト以下に制限すれば影響しない
3. argon2id の利点（GPU 耐性）は、**575 の脅威モデルでは決定的でない**。守るのは投稿の閲覧・投稿権限であり、金銭や機密ではない

argon2id へ移行する余地は残す。ハッシュ文字列は方式を識別できる形式で保存されるため、
**保存済みのハッシュを読みながら新方式へ移す**ことができる。

### 存在しない識別名とパスワード誤りを区別しない

```
❌ 「そのユーザーは存在しません」→ 識別名の存在を教えてしまう
✅ 「識別名またはパスワードが違います」
```

利用者の存在有無が分かると、識別名の総当たりで**登録済みの利用者を列挙**できる。
応答の内容だけでなく、**処理時間でも区別できてはならない**。
利用者が見つからない場合もダミーのハッシュ検証を行い、応答時間を揃える。

### セッションの検証は毎リクエスト DB を引く

[ADR-0006](../adr/0006-authentication.md#6-結果) が「認証のたびに DB へアクセスする」ことを
受け入れた代償である。主キー検索であり、[NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の
300ms に対して無視できる範囲と見込んでいる。**実測して確かめる**（#9 と同じ扱い）。

### レート制限を別 Issue に分ける理由

[基本設計 05](../design/basic/05-api.md#レート制限) は `POST /auth/login` に
5回/分/IP、`POST /auth/signup` に 3回/時/IP を定めている。
しかし実装方法が [NFR-03-02](../requirements/01-requirements.md#nfr-03-拡張性) と衝突する。

> セッション・キャッシュ等の状態はサーバーのメモリ・ローカルストレージに保持しないこと

api は複数インスタンスで動くため、**プロセス内のカウンタでは制限にならない**
（インスタンスが増えるほど実際の上限が緩む）。かといって共有ストアを置くなら、
[ADR-0006 が Redis を却下した判断](../adr/0006-authentication.md#案2redisを却下する理由)と整合を取る必要がある。

これは認証の実装とは独立した設計判断であり、**この Issue に混ぜると両方の完了条件が曖昧になる**。
別 Issue で扱い、必要なら ADR を起こす。
