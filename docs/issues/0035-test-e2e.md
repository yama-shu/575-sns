## 背景・目的

[詳細設計 04](../design/detail/04-test-design.md) のテストの配分で、頂点に置いた **E2E テスト（少数）** を実装する。

```
E2E テスト（少数）      主要な導線が通ることの確認
結合テスト（中程度）    api ↔ DB、api ↔ prosody
単体テスト（多数）      判定アルゴリズム、業務ロジック
```

**いま3つのサービスをまたぐ確認が無い。** 単体テストと結合テストは各サービスの中で閉じており、
「ブラウザで開いて、詠んで、読める」ことは**人が手で確かめている**だけである。

M4 の 13 画面が揃ったため、着手できる。

## 使う道具を決める

**Playwright を使う。**

| 候補 | 判断 |
| --- | --- |
| **Playwright** | 採用。TypeScript が第一級で web と言語が揃う。待機・アサーション・失敗時の痕跡（スクリーンショット・トレース）が最初から揃っている |
| 素の CDP スクリプト | 採らない。検証で使い捨てのものを書いたが、待機もアサーションも自前で、**同じ誤りを何度も踏んだ**（要素の取り違え、眠って待つ、ハイドレーション前の操作） |
| Cypress | 採らない。別プロセスのブラウザを操る形ではなく、独自の実行環境に寄せる必要がある |

**リポジトリの根に `e2e/` を置く。** 対象は web だけではなく、
db・prosody・api・web を通した振る舞いである。`web/` の下に置くと、
api だけが変わったときに動かない CI 設定になる。

## 実装上の注意

### テストごとに利用者を作る

**固定の利用者を共有しない。** 並列実行で互いの状態を壊し、
「単体では通るのに揃えると落ちる」形の不安定さになる。

テストごとに一意な識別名で登録する。575 は登録に招待もメール確認も要らないため、
これができる。

### 判定は本物を使う

prosody をモックしない。**つないだときに通るかを見るのが目的**である。
モックすると、判定エンジンと画面のつなぎ目という一番確かめたい部分が抜ける。

### 眠って待たない

`waitForTimeout` を使わない。**検証で何度も踏んだ誤りである**
（[#71](https://github.com/yama-shu/575-sns/issues/71) で開発モードの初回コンパイルに引っかかり、実装を疑った）。

Playwright の `expect(...).toBeVisible()` などは条件が満たされるまで待つ。
そちらを使う。

### CI で動かす

`docker compose up -d --wait` でスタックを起動してから実行する。
`compose.yaml` には healthcheck と `depends_on` の条件が入っているため、
起動完了を待てる。

**web / api / prosody のいずれかが変わったときに動かす。**
E2E は3つをまたぐため、web の変更だけを見ていると api の退行を見逃す。
