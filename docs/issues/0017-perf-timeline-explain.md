## 背景・目的

[基本設計 03 §3](../design/basic/03-database.md#実行計画の確認を必須とする) が、
タイムラインの2クエリについて実行計画の取得を**必須**としている。

> 上記2クエリは 575 で最も頻繁に実行される。
> 実装時に `EXPLAIN ANALYZE` を取得し、記録に残す。

[ADR-0005](../adr/0005-timeline-strategy.md) も、Pull 型（fan-out on read）を採用した代償として
「実装時に `EXPLAIN ANALYZE` を取得し、Seq Scan が発生していないことを確認する」を前提に置いている。

[#38](https://github.com/yama-shu/575-sns/issues/38) で実装は済んでいるが、**確認できたのは 3,000 行までである。**
また `blocks` の除外については、行数が少なくプランナが Seq Scan を選ぶため判断できなかった。

```
->  Seq Scan on blocks b  (cost=0.00..1.00 rows=1 width=16)
      Filter: ((blocker_id = 1) OR (blocked_id = 1))
```

規模を伴う測定を行い、記録に残す。

## やること

- [ ] 測定用のデータ投入スクリプトを作る（再現できる形にする）
- [ ] `posts` 10万行以上・`follows` / `blocks` / `likes` も相応の規模で投入する
- [ ] 両タイムラインの `EXPLAIN ANALYZE` を取得する
- [ ] カーソルが深いページでも速度が落ちないことを確認する
- [ ] `blocks` の除外がインデックスを使えているかを確認する
- [ ] `docs/perf/0002-timeline-explain.md` に記録する
- [ ] 必要ならインデックスを追加する（[下記](#インデックスの追加は測定してから決める)）

## 完了条件

- [ ] `posts` が 10万行以上ある状態で測定している（[基本設計 03 §3](../design/basic/03-database.md)）
- [ ] 全体タイムラインの `EXPLAIN ANALYZE` を記録している
- [ ] フォロー中タイムラインの `EXPLAIN ANALYZE` を記録している
- [ ] `posts` に Seq Scan が出ていない
- [ ] 実際に読んだ行数が `LIMIT` 前後に収まっている（早期終了している）
- [ ] `blocks` の除外がどう解決されるかを記録している
- [ ] **カーソルが深い位置でも実行時間が変わらない**ことを数値で示している
- [ ] `OFFSET` 方式との比較を数値で示している（[下記](#offset-との比較を残す)）
- [ ] 測定を再現する手順が記録に含まれている
- [ ] [NFR-01-02](../requirements/01-requirements.md#nfr-01-性能)（P95 < 300ms）に対する評価を記載している
- [ ] 測定環境のスペックを記録している

## やらないこと

- HTTP 経由の負荷試験。[#9](https://github.com/yama-shu/575-sns/issues/9) と同じ形の測定は、
  API が出揃ってから改めて行う（M5 の「本番構成で性能を再測定する」）
- タイムラインの実装変更。**測定してから判断する**
- 方式の変更（Push 型への移行）。ADR-0005 は移行の判断基準を
  「P95 が 300ms を超え続けること」としており、いまはその段階にない

## 実装上の注意

### 測定を再現できる形にする

[#9](https://github.com/yama-shu/575-sns/issues/9) と同じく、スクリプトで再現できるようにする。
手作業で投入したデータは、後から同じ条件を作り直せない。

`scripts/bench/` に置く。既存の `run.sh`（prosody 用）とは別物として分ける。

### `OFFSET` との比較を残す

[基本設計 03 §5](../design/basic/03-database.md#なぜ-offset-を使わないか) は
「`OFFSET` はページが深くなるほど線形に遅くなる」としているが、**この主張を数値で確かめていない。**

同じデータに対して両方を実行し、深いページでの差を記録する。
設計の判断が正しかったことの裏付けになる。

### インデックスの追加は測定してから決める

`blocks` の除外に追加のインデックスが要るかは、実測してから判断する。

主キーは `(blocker_id, blocked_id)` の順だが、双方向の条件は**両方の枝で
`blocker_id` を等値で絞る**ため、そのまま使えるはずである
（[#38 のコメント](https://github.com/yama-shu/575-sns/issues/38)）。
予防的に足さない。[基本設計 03 §3](../design/basic/03-database.md) の
「必要な場所にだけ張る」に従う。

### 投入するデータの偏りに注意する

全員が同じ数の投稿を持つデータでは、実際の分布と違う計画が選ばれうる。

| 対象 | 方針 |
| --- | --- |
| 投稿数 | 利用者ごとに偏らせる（多い人・少ない人を作る） |
| フォロー数 | [ADR-0005](../adr/0005-timeline-strategy.md) が「1ユーザーあたりの平均フォロー数」を監視指標にしている。現実的な値を選び、根拠を書く |
| ブロック | 少数で構わないが、0 件にはしない。0 件だとプランナが Seq Scan を選ぶ |

### `EXPLAIN ANALYZE` の前に `ANALYZE` を実行する

統計が古いままだと、プランナが実際の行数を知らずに計画を立てる。
投入後に `ANALYZE` を実行してから測定する。
これを忘れると、測定した計画が本番で再現しない。
