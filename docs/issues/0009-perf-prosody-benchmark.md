## 背景・目的

[ADR-0003](../adr/0003-morphological-analyzer.md#速度eの検証) で SudachiPy を選定した際、
**速度については実測せず「短文なら十分に速いはず」という見込みで判断した**。

ADR-0003 は「検証が必要な事項」として以下を明記している。

- 解析1件あたりの所要時間が [NFR-01-01](../requirements/01-requirements.md#nfr-01-性能)（P95 150ms）を満たすか
- 辞書ロード後のメモリ使用量が、想定インスタンス数で運用コストに収まるか

この Issue でその検証を行う。見込みを外していた場合、ADR-0003 を見直す。

## 依存

- `feat: prosody の判定 API とヘルスチェックを実装する`

## やること

- [ ] ベンチマークの実行環境を用意する（結果が再現できる形で）
- [ ] 判定 API の応答時間を測定する（同時50接続）
- [ ] 処理段階ごとの内訳を測定する（正規化 / 形態素解析 / モーラ計算 / 区切り探索）
- [ ] 辞書ロード後のメモリ使用量を測定する
- [ ] 辞書のロード所要時間を測定する
- [ ] 測定結果を記録に残す

## 完了条件

- [ ] P50 / P95 / P99 / エラー率が記録されている
- [ ] **P95 が 150ms 未満である**か、下回らない場合は原因が特定されている
- [ ] 処理段階ごとの内訳が判明し、ボトルネックがどこかを言える
- [ ] 辞書ロード後のメモリ使用量が数値で判明している
- [ ] 以下がすべて記録されている
  - [ ] 測定対象
  - [ ] 測定方法（ツールと設定）
  - [ ] 測定条件（同時接続数・入力サイズ・実行時間）
  - [ ] 測定環境の構築方法
  - [ ] 構築された測定環境のスペック
  - [ ] 測定結果

## やらないこと

- 限界性能の測定（どこまで捌けるか）。想定規模に対する充足確認が目的
- 最適化そのもの。ボトルネックが判明し、かつ目標を満たさない場合に別 Issue を立てる

## 測定の設計

### 入力データ

実際の投稿を模した17モーラ前後の文を用意する。
**同じ文を繰り返さない**。キャッシュが効いて実態より速く見える。

| 種別 | 件数 | 意図 |
| --- | --- | --- |
| 定型に区切れる文 | 100 | 最も一般的なケース |
| 許容に区切れる文 | 50 | ズレの判定を通る |
| 総モーラ数で弾かれる文 | 50 | **早期リターンの効果を確認する** |
| C単位で失敗し A単位で成功する文 | 50 | **最悪ケース（2回解析する）** |

**最悪ケースを必ず含める。** 定型の文だけで測ると、
段階的探索が発生したときの実態を見誤る。

### 記録の残し方

数値だけを残しても、後から「どういう条件だったか」が分からず再現できない。
[詳細設計 04 §8](../design/detail/04-test-design.md#8-性能テスト) に挙げた項目をすべて記録する。

Issue のコメント欄に測定のたびに追記し、**時系列で追える形**にする。
本文を上書きすると、改善の経過が消える。

## 想定される結果と対応

| 結果 | 対応 |
| --- | --- |
| P95 < 150ms | 見込みどおり。ADR-0003 の判断が正しかったことを ADR に追記する |
| P95 が 150〜300ms | ボトルネックを特定し、改善 Issue を立てる。デバウンスの調整も検討する |
| P95 > 300ms | ADR-0003 の見直し。fugashi + UniDic への差し替えを検討する（`Tokenizer` を抽象化してあるため実装クラス1つの差し替えで済む） |
| メモリが想定を大きく超える | [ADR-0004](../adr/0004-hosting-and-infrastructure.md) のリソース配分を見直す |
