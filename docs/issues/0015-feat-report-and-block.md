## 背景・目的

[FR-05-01](../requirements/01-requirements.md#fr-05-健全性)（投稿を通報できる）と
[FR-05-02](../requirements/01-requirements.md#fr-05-健全性)（他ユーザーをブロックできる）を実装する。

M3 の2番目。タイムラインより先に着手するのは、
[BR-09](../design/basic/02-domain-model.md#関係に関するルール)「ブロックした相手の投稿は、すべての画面で表示されない」が
**すべての読み取り経路に波及する**ためである。後から足すと漏れる。

現時点で漏れが1件ある。
**[`GET /api/v1/posts/:id`](../../api/internal/usecase/post.go) がブロックを考慮していない**
（[#30](https://github.com/yama-shu/575-sns/issues/30) の時点でブロック機能が無かったため）。本 Issue で塞ぐ。

`blocks` / `reports` テーブルは [#20](https://github.com/yama-shu/575-sns/issues/20) で作成済み。
[#34](https://github.com/yama-shu/575-sns/issues/34) でブロックの参照（`IsBlocked`）だけ実装済み。

## 実装上の注意

### ブロックとフォロー解除を1トランザクションにする

[BR-08](../design/basic/02-domain-model.md#br-08-の設計意図) は
「ブロックすると、フォロー関係は双方向に解除される」と定めている。

```
BEGIN
  INSERT INTO blocks ... ON CONFLICT DO NOTHING
  DELETE FROM follows WHERE (follower_id = A AND followee_id = B)
                         OR (follower_id = B AND followee_id = A)
COMMIT
```

分けて実行すると、**ブロックはできたがフォローが残る**状態が生じうる。
ブロックしたのに相手のタイムラインに自分の投稿が流れ続けることになり、
BR-08 が防ごうとしたものがそのまま起きる。

### ブロックは双方向に見えなくする

[BR-09](../design/basic/02-domain-model.md#関係に関するルール) は
「ブロック**した**相手の投稿は表示されない」と一方向だけを定めている。
逆向き（ブロック**された**側から見て、ブロックした側の投稿）を定めていない。

**双方向に見えなくする。** 理由は3つ。

| 理由 | 説明 |
| --- | --- |
| 片方向だと目的を達しない | ブロックされた側は投稿を読み続け、いいね・通報もできる。「見られたくない」という意図（[BR-08 の設計意図](../design/basic/02-domain-model.md#br-08-の設計意図)）が満たされない |
| すでに片方向で実装した箇所と食い違う | [#34](https://github.com/yama-shu/575-sns/issues/34) で、ブロックされた側からのフォローは 404 にしている。投稿だけ見えるのは不整合 |
| 事実は漏れない | 404 は退会済み・存在しない投稿と区別がつかない（[BR-10](../design/basic/02-domain-model.md#関係に関するルール)） |

基本設計 02 に追記する。要件（FR-05-02）は「ブロックしたユーザーの投稿は表示されない」
としか書いていないが、これに反するものではない。

### 通報は投稿が見えることを前提にする

ブロックした相手の投稿は見えないため、通報もできない。
見えないものを通報する経路が無いためである。

削除済みの投稿も通報できない。運営が対応する対象がすでに無い。

### 通報の重複は DB の UNIQUE 制約で防ぐ

`reports_reporter_id_post_id_key` がある。
事前に存在確認してから INSERT すると、確認と INSERT のあいだに
同じ操作が挟まったときに制約違反になり 500 を返す。

制約違反を捕まえて `ALREADY_REPORTED` に変換する
（[#25](https://github.com/yama-shu/575-sns/issues/25) の `HANDLE_TAKEN` と同じ方式）。

### 通報は冪等にしない

ブロックは `PUT`（冪等）だが、通報は `POST` で 409 を返す。

| | 冪等か | 理由 |
| --- | :---: | --- |
| ブロック | ✅ | 「ブロックしている状態にする」という要求。何度でも同じ結果 |
| 通報 | ❌ | 「通報を1件作る」という要求。2件目は作らないが、**作られなかったことを伝える必要がある** |

通報が受理されたかどうかは利用者にとって意味が違う。
黙って 201 を返すと「通報が届いた」と誤解する。

### 自分自身の通報は DB では防げない

[BR-07](../design/basic/02-domain-model.md#関係に関するルール)（自分の投稿を通報できない）は
`reports.reporter_id` と `posts.author_id` の突き合わせが必要で、
単一行の CHECK 制約では表現できない（マイグレーションにも記載あり）。
アプリケーション側で担保する。

BR-06（自分をブロックできない）は `blocks_not_self_check` で DB 側にもある。

### `GET /posts/:id` の既存の漏れを塞ぐ

現在の実装は公開範囲（`public` / `followers`）しか見ておらず、ブロックを見ていない。
`usecase.Post.Get` にブロックの確認を追加する。

閲覧者が未ログインの場合はブロックの確認をしない。
誰でもない相手をブロックすることはできないためである。
