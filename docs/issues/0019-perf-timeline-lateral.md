## 背景・目的

[docs/perf/0002](../perf/0002-timeline-explain.md) の測定で、フォロー中タイムラインが**投稿総数に比例して悪化する経路**を持つことが分かった。

設計が想定したインデックス #7（`(author_id, id DESC)`）が使われず、`posts_pkey` を逆順に辿って1行ずつ絞る計画になる。読む行数は「20 ÷ フォロー先の投稿が全体に占める割合」に比例する。

| 測定の主体 | 割合 | 読んだ行数 | 実行時間（5回の中央値） |
| --- | ---: | ---: | ---: |
| 利用者1 | 62.02% | 22 | 0.836 ms |
| 利用者700 | 1.25% | 2,259 | 1.717 ms |
| 利用者999（1人だけフォロー） | 0.03% | **74,549** | **29.218 ms** |

いまは [NFR-01-02](../requirements/01-requirements.md#nfr-01-性能)（P95 < 300ms）を満たしている。

> **投稿が増えたときの値は測定していない。** 読む行数が投稿総数に比例することは
> 計画の形から言えるが、「10 倍で 292 ms」といった数値は外挿であり、
> 実測していない。実際に投入して確かめるのは本 Issue の作業に含める。

## やらないこと

- 全体タイムラインの変更。20 行を読んで 20 件を返しており、問題がない
- Push 型（fan-out on write）への移行。[ADR-0005](../adr/0005-timeline-strategy.md) は判断基準を「P95 が 300ms を超え続けること」としており、その段階にない

## 実装案

```sql
SELECT t.* FROM (
  SELECT p.* FROM follows f
  JOIN LATERAL (
    SELECT * FROM posts p
    WHERE p.author_id = f.followee_id AND p.status = 'published' AND p.id < :cursor
    ORDER BY p.id DESC LIMIT :limit
  ) p ON true
  WHERE f.follower_id = :me
) t ORDER BY t.id DESC LIMIT :limit;
```

測定済みの結果。

| 測定の主体 | フォロー数 | 現行 | `LATERAL` |
| --- | ---: | ---: | ---: |
| 利用者1 | 150 | **0.836 ms** | 3.309 ms |
| 利用者700 | 50 | 1.717 ms | **0.534 ms** |
| 利用者999 | 1 | 29.218 ms | **0.222 ms** |

```
->  Index Only Scan using posts_author_timeline_idx on posts p
      (actual time=0.009..0.010 rows=20.00 loops=50)
```

### 注意すべき点

**フォロー数が多い利用者では現行のほうが速い。** 利用者1（150 フォロー）で 0.836 ms 対 3.309 ms と、`LATERAL` が 4 倍遅い。現行は 22 行しか読まないのに対し、`LATERAL` は 150 × 20 = 3,000 行を読んでから並べ替えるためである。

**どちらが常に速いというものではない。**

書き換えるのは、悪化の上限が「フォロー数 × `limit`」で決まり、**投稿総数に依存しなくなる**ためである。読む行数の最大値を予測できることに価値がある。

各フォロイーから `limit` 件ずつ取れば、そのうち上位 `limit` 件が全体の上位 `limit` 件と一致する。1人から `limit` 件を超えて選ばれることはないため、取りこぼしは起きない。この不変条件をテストで固定する。
