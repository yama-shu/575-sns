## 背景・目的

api から prosody の `POST /v1/analyze` を呼べるようにする。

現在の [`api/internal/prosody/client.go`](../../api/internal/prosody/client.go) は
`/readyz` を叩く `Ping` しか持たない。判定を呼ぶ実装が無いため、
**投稿（`POST /api/v1/posts`）を実装できない**。投稿はモーラ数・区切り位置・判定結果を
保存する必要があり、それらの供給元が prosody だけである。

同時に、prosody が遅くなったり落ちたりしたときに api を巻き込まない防御を入れる。
[基本設計 01 §5](../design/basic/01-architecture.md#5-縮退運転) は
「閲覧系は一切影響を受けない。投稿だけができなくなる」と定めているが、
防御が無ければタイムライン取得まで道連れになる。

```
prosody の応答が 30 秒かかるようになる
  → api のリクエスト処理が 30 秒間ブロックされる
  → api の接続プールが埋まる
  → タイムライン取得のリクエストも処理できなくなる
  → 判定だけの障害が、サービス全体の障害になる
```

## やること

- [ ] `Client.Analyze` を実装する（`POST /v1/analyze`）
- [ ] レスポンスを `domain` の型へ変換する（[下記](#prosody-の型を上位へ漏らさない)）
- [ ] タイムアウト 1 秒を設定する
- [ ] リトライ 1 回・間隔 100ms + ジッタを実装する
- [ ] サーキットブレーカーを実装する（[下記](#サーキットブレーカーの状態遷移)）
- [ ] 失敗を `PROSODY_UNAVAILABLE` / `UPSTREAM_TIMEOUT` に対応付ける
- [ ] `event: prosody_call_failed` の構造化ログを出す
- [ ] `POST /api/v1/prosody/check` を実装する（[下記](#判定エンドポイントを同じ-issue-に含める理由)）
- [ ] 単体テストを書く（`httptest` で prosody を模し、遅延・失敗・回復を注入する）

## 完了条件

- [ ] `POST /api/v1/prosody/check` が [基本設計 05](../design/basic/05-api.md#post-apiv1prosodycheck) の形式で返る
- [ ] 破調・`unknown` が **200 で返る**（判定を求められて判定を返しているため）
- [ ] `unknown` のとき `unreadable` に読めなかった語が入る
- [ ] prosody を停止した状態で `PROSODY_UNAVAILABLE` の 503 が返る
- [ ] prosody を 1 秒以上遅延させると `UPSTREAM_TIMEOUT` の 504 が返る
- [ ] 直近 20 回中 10 回以上失敗するとブレーカーが開く
- [ ] 開放中は **prosody へ HTTP リクエストを送らない**（呼び出し回数で検証する）
- [ ] 開放から 30 秒後に半開になり、1 件だけ試行する
- [ ] 半開の試行が成功すると閉じ、失敗すると再び開く
- [ ] リトライが 1 回だけ行われる（呼び出し回数で検証する）
- [ ] prosody 停止中でも `GET /api/v1/me` が 200 を返す（縮退運転の確認）
- [ ] ログに投稿本文が出ていない（[詳細設計 03](../design/detail/03-error-handling.md#ログに出してはいけないもの)）
- [ ] C1 カバレッジ 90% 以上（[NFR-05-04](../requirements/01-requirements.md#nfr-05-保守性運用性)）
- [ ] `gofmt` の差分がなく、`golangci-lint` が 0 issues

## 実装上の注意

### サーキットブレーカーの状態遷移

[詳細設計 03 §4](../design/detail/03-error-handling.md#サーキットブレーカー) が定めた値をそのまま使う。

| 遷移 | 条件 |
| --- | --- |
| `Closed` → `Open` | 直近 20 回中 10 回以上失敗 |
| `Open` → `HalfOpen` | 30 秒経過 |
| `HalfOpen` → `Closed` | 試行が成功 |
| `HalfOpen` → `Open` | 試行が失敗 |

`Open` のあいだは **prosody を呼ばずに即座に失敗させる**。
死んでいると分かっているサービスを呼び続けると、api 側はタイムアウトを待つ分だけ
リソースを消費し、prosody 側は再起動して回復しようとしているところに負荷がかかる。

### タイムアウトとリトライ

| 項目 | 値 | 理由 |
| --- | --- | --- |
| タイムアウト | 1 秒 | [NFR-01-01](../requirements/01-requirements.md#nfr-01-性能) の 150ms に対し十分な余裕。1 秒かかるのは異常 |
| リトライ | 1 回 | 判定は副作用がないため安全にリトライできる |
| リトライ間隔 | 100ms + ジッタ | 全クライアントが同時にリトライして波を作らないため |

リトライを 1 回に限るのは、過負荷で遅くなっている相手に対してリトライが追加の負荷になるため。
回数を増やすほど回復を妨げる。

**タイムアウトはリクエスト全体に掛ける。** 1 秒 × 2 回で 2 秒待つと、
1 秒に決めた意味が無くなる。

### 状態をプロセス内に持つことの整理

ブレーカーの状態はプロセス内のメモリに持つ。
[NFR-03-02](../requirements/01-requirements.md#nfr-03-拡張性)（サーバーのメモリに状態を持たない）に
反するように見えるが、これは**インスタンス間で共有する必要がない状態**である。

| | レート制限 | サーキットブレーカー |
| --- | --- | --- |
| 守る対象 | 利用者ごとの回数 | 自インスタンスの資源 |
| 共有しないと | 上限がインスタンス数倍に緩む | 各インスタンスが自分の観測で判断するだけ |
| 判定の誤り | 仕様違反になる | 発生しない（自分が失敗したかどうかは自分が知っている） |

共有ストアを置くと、ブレーカーのために新しい単一障害点を作ることになる。

### prosody の型を上位へ漏らさない

[詳細設計 02 §2](../design/detail/02-class-design.md#2-api-のパッケージ構成) の
「すべての依存は domain へ向かう」に従う。usecase は prosody の JSON の形を知らない。

`verdict` / `reason` は文字列のまま扱わず、`domain` の型に変換する。
prosody が値を増やしたときに、変換の時点で気づける。

### 判定エンドポイントを同じ Issue に含める理由

クライアントだけを実装しても、呼び出す先が無いため**実機で確認できない**。
完了条件を「単体テストが通る」までしか書けず、
縮退運転（prosody 停止時に閲覧系が動く）を確かめられない。

`POST /api/v1/prosody/check` は prosody の応答をほぼそのまま転送するだけで、
業務ロジックを持たない。クライアントの検証手段として最小である。

### キャッシュを入れない

同じ本文が繰り返し判定される場面はある（入力中のデバウンス後）が、
[#9 の測定](../perf/0001-prosody-benchmark.md)で判定は 0.04ms 前後、
応答時間 6.98ms の 99% が HTTP の往復と分かっている。
キャッシュで削れるのは 1% に満たない。
状態を増やす代償に見合わないため入れない。
