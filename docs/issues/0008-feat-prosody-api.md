## 背景・目的

これまでに実装した判定ロジックを、HTTP サービスとして公開する。
api から呼び出せる状態にし、判定エンジンを単体で完成させる。

- `feat: 五七五の区切り探索を実装する`

- [ ] `ProsodyAnalyzer` を実装する（各コンポーネントを束ねる制御のみ）
- [ ] `POST /v1/analyze` を実装する
- [ ] `GET /healthz`（liveness）を実装する
- [ ] `GET /readyz`（readiness）を実装する
- [ ] 起動時に辞書を**同期的に**ロードする
- [ ] 構造化ログを出力する（`request_id` を含む）
- [ ] [詳細設計 04 §6](../design/detail/04-test-design.md#6-判定エンジン全体の受け入れテスト) の TC-AC-01〜10 をテストとして書く

- [ ] TC-AC-01〜10 がすべて通る
- [ ] `verdict` が `teikei` / `kyoyo` / `hacho` / `unknown` の4値を正しく返し分ける
- [ ] `hacho` のとき `reason` が `TOO_FEW_MORA` / `TOO_MANY_MORA` / `NO_VALID_SPLIT` を返し分ける

## やらないこと

- 認証。prosody はクラスタ内部からのみ到達可能とする（別途 NetworkPolicy で担保）

- 永続化。prosody は状態を持たない

## 実装上の注意

### 辞書を遅延初期化しない

「最初のリクエストが来たときにロードする」実装にすると、
複数のリクエストが同時に到着したときに二重ロードが起きうる。
それを防ぐロックは、以後すべてのリクエストで取得され続けるオーバーヘッドになる。

**起動時に同期ロードする。** この問題自体が発生しなくなる。

### `/readyz` を実装しないと何が起きるか

辞書のロードには時間がかかる。
`/readyz` がなければ、Pod の再起動やスケールアウトのたびに
**ロード中の Pod へトラフィックが流れてタイムアウトする**。

`/healthz`（プロセスが生きているか）と `/readyz`（処理できる状態か）は別物である。
両方を実装する。

### 破調はエラーではない

`POST /v1/analyze` に破調の文が来ても、**HTTP 200 を返す**。
判定を求められて判定を返しているため、リクエストは成功している。

「破調だから投稿を拒否する」のは 575 の業務ルールであり、api の責務。
prosody にこの判断を持たせない。
