## 背景・目的

[#52](https://github.com/yama-shu/575-sns/issues/52)（投稿作成画面）の完了条件に
「**読み不明**: 読めなかった語が明示される」がある。
実装前に実機で `unknown` を出そうとしたところ、**どんな入力でも出せなかった**。

原因は [`prosody/src/prosody/reading.py`](../../prosody/src/prosody/reading.py) の
`_resolve_one` の優先順位にある。

```python
# 解析器が読みを返したならそれを使う
if token.reading:
    return token.reading
```

**SudachiPy は読めなかった語に対して、表層をそのまま読みとして返す。**

```
$ docker compose exec -T prosody python -c "..."
'彁' '彁' ('名詞', '普通名詞')     ← 読みではなく表層が返る
'甃' 'イシダタミ' ('名詞', '普通名詞')
'龘' '龘' ('名詞', '普通名詞')
```

`token.reading` が空にならないため、`_resolve_one` は `None` を返す経路に到達しない。

## 何が壊れているか

### 1. 読めない語が1モーラとして数えられる

```
$ curl ... -d '{"body":"彁"}'
verdict=hacho total_mora=1 reading='彁'
```

**`彁` は読みではない。** これを1モーラと数えた結果が判定に混ざる。

### 2. `unknown` が実質的に到達不能

[詳細設計 01 §4](../design/detail/01-prosody-algorithm.md#4-読みが取得できない場合) は
読めない語を `unknown` として返すと定めている。
[基本設計 04 §3](../design/basic/04-screens.md#判定結果の表示パターン) は
その結果を「❓ 読み方が分かりません」として、読めなかった語を明示するとしている。

**この経路は実際の入力では動いていない。**
既存のテストは解析器を差し替えて経路だけを確かめており
（`test_読めない語があると破調ではなく判定不能になる`）、
本物の SudachiPy と組み合わせたときに到達しないことを検出できていなかった。

`hacho` になるため、正しく詠んだ利用者に
「五七五になっていません」と伝えることになる。
[詳細設計 01](../design/detail/01-prosody-algorithm.md) が
「読めなかっただけの句にそう伝えるのは誤りで、直しようがない」と述べている状態そのものである。

### 3. 数値読み変換が使われていない

同じ優先順位により、`numbers.read` も呼ばれない。

| 入力 | [詳細設計 01 §4 の表](../design/detail/01-prosody-algorithm.md#数値読み変換) | `numbers.read`（実装済み） | 実際に使われる読み |
| --- | --- | --- | --- |
| `10` | ジュウ（2モーラ） | ジュウ（2） | **イチレイ（4）** |
| `300` | サンビャク | サンビャク（4） | **サンレイレイ（6）** |
| `2024` | ニセンニジュウヨン（8モーラ） | ニセンニジュウヨン（8） | **ニレイニヨン（5）** |

`10` を「イチレイ」と読むのは日本語として誤りである。

**この項目は既知だった。** `test_数字にも読みが付く` が
「変換は解析器を差し替えたときの予備である」と記録している。
しかし [詳細設計 01 §4](../design/detail/01-prosody-algorithm.md#4-読みが取得できない場合) は
変換が働く前提で書かれており、**ドキュメントと実装が食い違ったままになっている**。

## やること

- [ ] 解析器の読みが**カタカナでない**場合は採用しない
- [ ] 数字は解析器の読みより**数値読み変換を優先する**
- [ ] [詳細設計 01 §4](../design/detail/01-prosody-algorithm.md#4-読みが取得できない場合) のフローチャートを実装に合わせる
- [ ] 本物の SudachiPy を使ったテストを足す（差し替えでは検出できなかったため）

## 完了条件

- [ ] 読めない語を含む本文が `unknown` になり、`unreadable` にその語が入る
- [ ] 上記が**本物の SudachiPy を通した経路**で確認できる
- [ ] `2024` が `ニセンニジュウヨン`（8モーラ）として数えられる
- [ ] `10` が `ジュウ`（2モーラ）として数えられる
- [ ] 既存の判定結果が変わらないことを、既存のテストで確かめる
- [ ] ドキュメントの表と実装が一致する
- [ ] `./scripts/check.sh` が通る

## やらないこと

- 読みの手動修正（[FR-02-09](../requirements/01-requirements.md#fr-02-投稿詠む) は Could）
- 辞書の追加・差し替え（`SudachiDict-full` などの検討は別）
- 助数詞との連濁（`1本` → `イッポン`）。[詳細設計 01 §4](../design/detail/01-prosody-algorithm.md#4-読みが取得できない場合) が既知の誤差として受け入れている
- 画面側の対応（[#52](https://github.com/yama-shu/575-sns/issues/52) で扱う）

## 実装上の注意

### 「読みが空か」では判定できない

[詳細設計 01 §4](../design/detail/01-prosody-algorithm.md#4-読みが取得できない場合) のフローチャートは
分岐を「読みが空か」としている。**SudachiPy に対してはこの条件が成立しない。**

判定条件を「読みがカタカナか」に変える。
カタカナ以外が混じった読みは、解析器が読みを付けられなかった印である。

長音符（`ー`）はカタカナの範囲に含まれる。

### 数字を解析器より先に扱う

フローチャートは解析器の読みを最優先にしている。
数字については**先に数値読み変換を行う**ように改める。

SudachiPy は数字にも読みを返すため、後段に置くと到達しない。

### 判定結果が変わる

モーラ数が変わるため、**数字を含む既存の投稿の判定は変わりうる**。
保存済みの投稿は判定結果を持っている（[基本設計 01 §4](../design/basic/01-architecture.md)）ため
表示は変わらないが、同じ本文を再投稿すると結果が違うことはある。

MVP 前で投稿数が少ないため、移行は行わない。

### 差し替えたテストでは足りない

既存のテストは `Tokenizer` を差し替えて経路を確かめており、
**本物の解析器と組み合わせたときの挙動を見ていない**。
だから今回の不具合が残った。

本物の SudachiPy を使うテストを足す。
