## 背景・目的

3言語（TypeScript / Go / Python）を扱うため、手元での確認だけでは
「別の言語のサービスを壊していないか」が分からない。

また [詳細設計 04](../design/detail/04-test-design.md) で
prosody の C1 カバレッジ 100% を目標に置いている。
これは自動で計測・記録され続けなければ維持できない。

## やること

- [ ] Pull Request をトリガーに CI を実行する
- [ ] 3サービスそれぞれで lint を実行する
- [ ] 3サービスそれぞれで単体テストを実行する
- [ ] カバレッジを計測し、結果を PR にコメントする
- [ ] Docker イメージのビルドが通ることを確認する
- [ ] 依存パッケージの脆弱性を検査する
- [ ] 変更のあったサービスのみを実行する（不要なジョブを走らせない）

## 完了条件

- [ ] PR を作成すると CI が自動で走る
- [ ] lint エラー・テスト失敗があるとマージできない
- [ ] prosody のカバレッジが目標を下回った場合に検知できる
- [ ] `main` ブランチへの直接 push が禁止されている
- [ ] CI の実行時間が5分以内に収まる

## やらないこと

- CD（デプロイ）の構築（別 Issue）
- E2E テストの実行（テストが存在してから）

## 検討が必要な点

### 変更のあったサービスのみ実行する

毎回3サービス全部をビルド・テストすると、
prosody だけの変更でも web のビルドを待つことになる。

変更されたパスに応じてジョブを分岐させる。
ただし**共通の定義（OpenAPI 等）が変わった場合は全サービスを回す**。
ここを間違えると、契約の変更で壊れたサービスを見逃す。

### 費用

パブリックリポジトリであれば実行時間の制限がない
（[ADR-0004](../adr/0004-hosting-and-infrastructure.md#コンポーネントごとの選定と費用)）。

プライベートにする場合は無料枠に上限があるため、
実行時間の削減がそのまま費用の問題になる。
**リポジトリを公開するかどうかを、この Issue の着手前に決める。**

公開する場合、[NFR-04-07](../requirements/01-requirements.md#nfr-04-セキュリティ)
（認証情報をコミットしない）の徹底が前提条件になる。
