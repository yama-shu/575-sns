## 背景・目的

[FR-05-03](../requirements/01-requirements.md#fr-05-健全性)（運営は通報された投稿を確認し、非表示化できる）を実装する。
[S-13 通報一覧](../design/basic/04-screens.md#1-画面一覧) の前提になる。

**通報は溜まるが、誰も処理できない。** [#64](https://github.com/yama-shu/575-sns/issues/64) で画面から通報できるようになったが、
受け取る側が無い。

いま欠けているものは3つある。

| 欠けているもの | 現状 |
| --- | --- |
| 運営を示す情報 | `users` に列が無い |
| 運営向けの経路 | `/api/v1/admin/*` が未実装 |
| 投稿を非表示にする手段 | `PostHidden` という定数があるだけで、書き込む箇所が無い |

**画面と分ける。** マイグレーション・認可・新しい経路が伴い、[#58](https://github.com/yama-shu/575-sns/issues/58) [#68](https://github.com/yama-shu/575-sns/issues/68) と同じ規模になる。

## 実装上の注意

### 権限を与える API を作らない

`users.is_admin` を真にする経路を作らない。**DB を直接更新する。**

権限を与える API は、壊れたときの被害が最も大きい経路になる。
運用者がひとりである以上、手作業で足りる。README に手順を書く。

```sql
UPDATE users SET is_admin = true WHERE handle = '...';
```

### 運営でない利用者には 404 を返す

403 を返すと、**運営向けの経路が存在することを教える**ことになる。
[BR-10](../design/basic/02-domain-model.md) が「見えないものの存在を教えない」としているのと同じ考え方で、
404 に揃える。未ログインも同じ。

### 非表示化と記録を分けない

`resolve` は投稿を `hidden` にし、通報を `resolved` にする。
**1トランザクションで行う。**

分けると「投稿は消えたが通報が未対応のまま」「通報は閉じたが投稿が見えたまま」が生じる。
[#36](https://github.com/yama-shu/575-sns/issues/36) のブロックが BR-08 のために1トランザクションにしたのと同じである。

### 同じ投稿への通報をまとめて閉じる

[基本設計 02 §4](../design/basic/02-domain-model.md) が定めている。

> 運営は投稿単位で対応し、その投稿に紐づく未対応の通報をまとめて処理する。

1件だけ閉じると、**すでに非表示にした投稿の通報が一覧に残り続ける**。
同じトランザクションで、同じ投稿への未対応の通報をすべて閉じる。

却下も同じ扱いにする。上の一文は対応と却下を分けていない。

### 古い順に返す

タイムラインは新しい順だが、**通報は古い順に出す**。
待たせている順に処理するためである。カーソルの向きも逆になる。

インデックス #14（`(created_at) WHERE status='pending'`）がこの並びのために作ってある。

### 投稿の本文を一覧に載せる

運営は投稿を見なければ判断できない。**通報一覧に本文と投稿者を含める。**

1件ずつ引くと N+1 になる。JOIN で1回にまとめる。

### 非表示は可視性の判定に既に入っている

`visibility.resolve` は `post.Status != PostPublished` を 404 にしており、
タイムラインの問い合わせも `status='published'` で絞っている。
**非表示にすれば、それだけで見えなくなる。** 追加の除外は要らない。
