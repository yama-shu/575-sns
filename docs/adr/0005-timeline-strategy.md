# ADR-0005: タイムラインの実現方式

| 項目 | 内容 |
| --- | --- |
| 状態 | **承認** |
| 決定日 | 2026-08-06 |
| 関連 | [要件定義 Q-04](../requirements/01-requirements.md#10-未決事項) / [FR-03-02](../requirements/01-requirements.md#fr-03-閲覧) / [NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) |

---

## 1. 背景

[FR-03-02](../requirements/01-requirements.md#fr-03-閲覧) の「フォロー中タイムライン」を、
どのタイミングで組み立てるかを決める。

SNS のタイムラインには古典的に2つの方式があり、
どちらを選ぶかでデータモデル・性能特性・整合性の扱いがすべて変わる。

---

## 2. 決定を左右する要因

| # | 評価軸 | 説明 |
| --- | --- | --- |
| A | **応答速度** | [NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の P95 300ms を満たすこと |
| B | **整合性** | 投稿削除・ブロック・フォロー解除が即座に反映されること |
| C | **追加リソース** | 無料枠の制約下で、メモリ・ストレージを追加消費しないこと（[C-04](../requirements/01-requirements.md#9-制約と前提)） |
| D | **実装の単純さ** | 1人開発で保守できること（[C-01](../requirements/01-requirements.md#9-制約と前提)） |

---

## 3. 選択肢

### 案1: Pull 型（fan-out on read）

タイムラインを**読むたびに**クエリで組み立てる。

```sql
-- 概念的なクエリ（実際のカラム名は基本設計で定義する）
SELECT p.* FROM posts p
JOIN follows f ON f.followee_id = p.author_id
WHERE f.follower_id = :me
ORDER BY p.id DESC
LIMIT 20;
```

### 案2: Push 型（fan-out on write）

**投稿された瞬間に**、その投稿者のフォロワー全員のタイムラインへ書き込む。

```
ユーザーAが投稿
  → Aのフォロワー 500人分のタイムラインに、投稿IDを500行 INSERT
  → 各ユーザーは自分のタイムラインを読むだけ（JOIN 不要）
```

### 案3: ハイブリッド

通常のユーザーは Push 型、フォロワーが極端に多いユーザー（インフルエンサー）だけ Pull 型にする。

---

## 4. 比較

| | 案1: Pull 型 | 案2: Push 型 | 案3: ハイブリッド |
| --- | --- | --- | --- |
| **A. 読み込み速度** | 🔺 JOIN が必要 | ✅ 単一テーブル走査 | ✅ |
| **A. 書き込み速度** | ✅ 1行 INSERT | ❌ フォロワー数だけ INSERT | 🔺 |
| **B. 整合性** | ✅ 常に最新 | ❌ 削除・ブロックの反映に追加処理が要る | ❌ |
| **C. 追加リソース** | ✅ 不要 | ❌ タイムライン用テーブル / Redis が必要 | ❌ |
| **D. 実装の単純さ** | ✅ クエリ1本 | 🔺 非同期ワーカーが必要 | ❌ 両方式の保守 |

### Push 型の書き込み増幅

Push 型は「読む人が多いほど得」だが、**書き込みが爆発する**。

```
フォロワー 500人のユーザーが1回投稿
  → 500行の INSERT

そのユーザーが投稿を削除
  → 500行の DELETE

あるユーザーがそのユーザーをブロック
  → 過去の投稿すべてを、そのユーザーのタイムラインから削除
```

さらに深刻なのは **B（整合性）** である。
[FR-05-02](../requirements/01-requirements.md#fr-05-健全性)（ブロック）と
[FR-05-03](../requirements/01-requirements.md#fr-05-健全性)（運営による非表示化）は、
**即座に反映されなければ意味がない機能**である。

Push 型では、これらの操作のたびに事前計算済みのタイムラインを
遡って修正する必要がある。修正が漏れると「ブロックしたはずの相手の投稿が見え続ける」
という、健全性機能として致命的な不具合になる。

### 案3 を却下する理由

ハイブリッドは Twitter 規模で有効な最適化だが、
**両方式のコードを保守する必要がある**。1人開発では割に合わない。
そもそも案2 を採る規模に達していない段階で、その最適化を導入する理由がない。

### Pull 型の弱点と、それが問題にならない理由

Pull 型の弱点は、フォロー数が増えると JOIN が重くなることである。

しかし 575 の想定規模は [NFR-01-03](../requirements/01-requirements.md#nfr-01-性能) で
**同時接続 1,000** としている。この規模では、
`follows` に適切な複合インデックスを張れば Pull 型で十分に応答できる。

加えて 575 には構造的な有利さがある。**投稿が必ず17音前後に収まる**ため、
1レコードのサイズが小さく、同じメモリでより多くの行をキャッシュできる。
一般的なテキスト SNS より Pull 型が有利に働く。

---

## 5. 決定

**案1（Pull 型 / fan-out on read）を採用する。**

### 前提とする実装方針

| 項目 | 方針 |
| --- | --- |
| ページネーション | **カーソル方式**（`WHERE id < :cursor`）を用いる。`OFFSET` は深いページで線形に遅くなるため使わない |
| インデックス | `follows(follower_id, followee_id)` と `posts(author_id, id DESC)` を前提とする。詳細は基本設計の DB 設計で定義する |
| ブロックの反映 | クエリ内で `NOT EXISTS (blocks)` により除外する。事前計算しないため常に最新 |
| 実行計画の確認 | 実装時に `EXPLAIN ANALYZE` を取得し、Seq Scan が発生していないことを確認する |

---

## 6. 結果

### この決定によって可能になること

- Redis 等のキャッシュ層を追加せずに済み、無料枠のメモリを判定エンジンに回せる
- ブロック・削除・運営による非表示化が、追加処理なしで即座に反映される
- タイムライン用のテーブルが不要になり、データモデルが単純になる

### この決定によって諦めること

- **ユーザー数が増えたときに、タイムライン取得が先に限界を迎える。**
  これは想定内であり、その時点でハイブリッド方式（案3）への移行を検討する。
  移行の判断基準は「タイムライン取得の P95 が 300ms を超え続けること」とする。
- インフルエンサー的なユーザーが現れた場合の最適化余地を、あらかじめ持たない。

### 監視すべき指標

| 指標 | 閾値 | 超えたときの対応 |
| --- | --- | --- |
| タイムライン取得の P95 | 300ms | クエリと実行計画を再確認。インデックスで解決しなければ方式変更を検討 |
| 1ユーザーあたりの平均フォロー数 | — | 増加傾向を観測する。JOIN の重さに直結するため |
