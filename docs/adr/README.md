# Architecture Decision Record (ADR)

設計上の分岐点に立ったとき、**どんな選択肢があり、どれを、なぜ選んだか**を1決定1ファイルで記録します。

## なぜ ADR を書くのか

設計書には「結論」しか書きません。結論だけを読んでも
「なぜこうなっているのか」「他の案は検討されたのか」が分からず、
半年後の自分や、後から参加した人が同じ議論をやり直すことになります。

ADR はその**過程**を残すためのものです。
特に「採用しなかった案」と「その理由」に価値があります。

## 運用ルール

### ファイル名

```
NNNN-短い英語のタイトル.md
```

連番は決定した順に振ります。欠番は作りません。

### 状態

| 状態 | 意味 |
| --- | --- |
| 提案 | 検討は済んでいるが、まだ承認されていない |
| 承認 | 採用が決定した。以降の設計はこれに従う |
| 却下 | 検討したが採用しなかった。記録として残す |
| 置換 | 後続の ADR によって覆された。どの ADR に置き換わったかを明記する |

**一度書いた ADR は書き換えません。** 決定が覆った場合は新しい ADR を起こし、
古い方の状態を「置換」に変更してリンクを張ります。
決定が変わった事実そのものが記録として重要だからです。

### 書く内容

1. **背景** — なぜ今この決定が必要なのか
2. **決定を左右する要因** — 何を重視して選ぶのか（評価軸）
3. **選択肢** — 検討した案すべて。採用しなかった案も必ず書く
4. **比較** — 各案のメリット・デメリット・トレードオフ
5. **決定** — どれを選んだか
6. **理由** — なぜそれを選んだか
7. **結果** — この決定によって何が可能になり、何を諦めたか
