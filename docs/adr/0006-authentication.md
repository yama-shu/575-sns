# ADR-0006: 認証方式

| 項目 | 内容 |
| --- | --- |
| 状態 | **承認** |
| 決定日 | 2026-08-06 |
| 関連 | [要件定義 Q-05](../requirements/01-requirements.md#10-未決事項) / [FR-01-02](../requirements/01-requirements.md#fr-01-アカウント) / [FR-05-04](../requirements/01-requirements.md#fr-05-健全性) / [NFR-03-02](../requirements/01-requirements.md#nfr-03-拡張性) |

---

## 1. 背景

ログイン状態をどう保持するかを決める。

この決定は [NFR-03-02](../requirements/01-requirements.md#nfr-03-拡張性)
（サーバーのメモリ・ローカルストレージに状態を持たない）と直接ぶつかる。
複数の api インスタンスのどれにリクエストが振られても、
同じログイン状態が見えなければならない。

---

## 2. 決定を左右する要因

| # | 評価軸 | 説明 |
| --- | --- | --- |
| A | **ステートレス性** | api がどのインスタンスでも同じ結果を返すこと（[NFR-03-02](../requirements/01-requirements.md#nfr-03-拡張性)） |
| B | **即時失効できるか** | 利用停止（[FR-05-04](../requirements/01-requirements.md#fr-05-健全性)）とログアウトが即座に効くこと |
| C | **追加リソース** | 無料枠を圧迫しないこと（[C-04](../requirements/01-requirements.md#9-制約と前提)） |
| D | **XSS 耐性** | トークンが JavaScript から読めない形で保持されること |

---

## 3. 選択肢

| 案 | 方式 |
| --- | --- |
| **案1** | セッション ID を Cookie、セッション実体を **PostgreSQL** に保存 |
| **案2** | セッション ID を Cookie、セッション実体を **Redis** に保存 |
| **案3** | **JWT** をクライアントに持たせる（サーバーは状態を持たない） |
| **案4** | 外部の認証サービス（Auth0 / Firebase Authentication など）に委譲 |

---

## 4. 比較

| | 案1: Cookie + PostgreSQL | 案2: Cookie + Redis | 案3: JWT | 案4: 外部サービス |
| --- | --- | --- | --- | --- |
| **A. ステートレス性** | ✅ 状態は DB | ✅ 状態は Redis | ✅ 状態なし | ✅ |
| **B. 即時失効** | ✅ 行を消すだけ | ✅ | ❌ **有効期限まで失効できない** | ✅ |
| **C. 追加リソース** | ✅ 既存の DB を使う | ❌ Redis の分のメモリ | ✅ 不要 | 🔺 無料枠に上限 |
| **D. XSS 耐性** | ✅ HttpOnly Cookie | ✅ HttpOnly Cookie | 🔺 保存場所による | ✅ |
| **読み取り性能** | 🔺 毎回 DB アクセス | ✅ 高速 | ✅ 検証のみ |  🔺 外部通信 |

### 案3（JWT）を却下する理由

**即時失効できないことが、健全性機能と両立しない。**

JWT はサーバーが状態を持たないため、一度発行したトークンは
**有効期限が切れるまで無効化できない**。

これは 575 では致命的である。

```
【起きること】
運営が不適切な投稿を繰り返すユーザーを利用停止にする（FR-05-04）
  → しかし、そのユーザーの JWT は有効期限まで生き続ける
  → 有効期限を1時間にしても、その1時間は投稿し放題

【ログアウトでも同じ問題】
ユーザーが共用 PC でログアウトする
  → サーバー側では何も起きない
  → Cookie を復元されればログインしたままになる
```

「失効リスト（ブラックリスト）を持つ」という回避策はあるが、
**それはもはやステートフルであり、JWT を選ぶ理由が消える。**
失効リストを DB に持つなら、最初からセッションを DB に持つ案1 と変わらない。
むしろトークン検証と失効リスト参照の二重管理になり、複雑度だけが増す。

### 案2（Redis）を却下する理由

技術的には最も素直な選択である。しかし
[ADR-0004](0004-hosting-and-infrastructure.md) の無料枠構成において、
**Redis に割り当てるメモリは prosody の辞書と競合する。**

セッション情報は「数千ユーザー × 数百バイト」程度で、
PostgreSQL に置いても負荷にならない量である。
この規模で Redis を追加導入するのは、リソース配分として合理的でない。

### 案4（外部サービス）を却下する理由

- 無料枠に月間アクティブユーザー数の上限があり、超えると課金が発生する（[C-04](../requirements/01-requirements.md#9-制約と前提)に反する）
- 認証という中核機能を外部に依存させると、その事業者の障害・仕様変更・料金改定を直接受ける
- 認証は自前で実装しても複雑度が過大にならない範囲である

---

## 5. 決定

**案1（Cookie + PostgreSQL セッション）を採用する。**

### 仕様

| 項目 | 決定 |
| --- | --- |
| セッション ID | 暗号論的に安全な乱数生成器で生成する。連番・推測可能な値を使わない |
| 保存先（サーバー） | PostgreSQL の `sessions` テーブル。詳細は基本設計の DB 設計で定義する |
| 保存先（クライアント） | Cookie。**`HttpOnly` / `Secure` / `SameSite=Lax`** を必ず付与する |
| 有効期限 | 30日。アクセスのたびに延長する（スライディング期限） |
| ログアウト | サーバー側のセッション行を削除し、Cookie を失効させる |
| 利用停止 | 対象ユーザーのセッション行をすべて削除する。**次のリクエストから即座に効く** |
| パスワード保存 | ソルト付きハッシュ（[NFR-04-01](../requirements/01-requirements.md#nfr-04-セキュリティ)）。平文・可逆暗号を使わない |

### Cookie 属性の意図

| 属性 | 効果 |
| --- | --- |
| `HttpOnly` | JavaScript から Cookie を読めなくする。XSS でトークンを盗まれても持ち出せない（[D](#2-決定を左右する要因)） |
| `Secure` | HTTPS 上でのみ送信する。平文通信での漏洩を防ぐ |
| `SameSite=Lax` | クロスサイトからのリクエストで Cookie を送らない。CSRF の主要な経路を塞ぐ |

---

## 6. 結果

### この決定によって可能になること

- 利用停止・ログアウトが次のリクエストから即座に効く
- api を何インスタンスに増やしても、セッションは DB で共有される
- Redis を追加せずに済み、無料枠のメモリを判定エンジンに回せる
- `HttpOnly` Cookie により、XSS からトークンを保護できる

### この決定によって諦めること

- **認証のたびに DB へアクセスする。** Redis に比べれば遅い。
  ただしセッション ID の主キー検索であり、[NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の
  300ms に対して無視できる範囲と見込む。実測で覆った場合は案2 を再検討する。
- **セッションテーブルが際限なく増える。** 期限切れセッションを削除する
  定期ジョブが必要になる。これは実装タスクとして計上する。
- モバイルアプリを作る場合、Cookie ベースの認証は Web ほど素直でない。
  [5.3 スコープ外](../requirements/01-requirements.md#53-スコープ外当面やらない) の範囲であり、
  必要になった時点で別途トークン発行方式を追加する。

### 検証が必要な事項

| 検証項目 | 判断基準 |
| --- | --- |
| セッション検索を含めた API 応答時間 | [NFR-01-02](../requirements/01-requirements.md#nfr-01-性能) の P95 300ms を満たすか |
| 期限切れセッションの削除ジョブ | テーブルサイズが単調増加していないこと |
